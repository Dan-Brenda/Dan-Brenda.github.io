Case study

Measured Size

One recommended bra size, translated into the size labels that 160+ brands actually use.

Live on the Chrome Web Store, Firefox Add-ons and the App Store. It just launched and has a small number of early users. measuredsize.com

  • 160+ brands supported
  • 450+ scoped build phases
  • 12,500+ automated tests per release
  • 8.5M answers replayed before release

The problem

Bra sizes don't carry over from brand to brand. A woman's usual size at one brand can be a size off at another, usually in the band or the cup. The band rides up or digs in, or the cup gaps or spills over. Then she either sends it back or wears a bra that doesn't fit.

I saw a gap in the market. No tool gave her the right size at whatever store she was shopping. I wanted one honest answer, in that brand's own size labels, right on the product page.

What I built

Measured Size takes a shopper's measurements, works out one recommended size, and translates it into each brand's own label. She sees the size to order at the brand she is looking at, instead of guessing from a generic chart.

  • Browser extension, live on the Chrome Web Store (which also covers Edge and Brave) and Firefox Add-ons (desktop and Android). It shows her size right on the product page.
  • iPhone and iPad app, live on the App Store.
  • Public fit API and MCP server on Cloudflare Workers, so other developers and AI assistants can ask for a size at a given brand. API documentation.

How I worked

I ran Measured Size as the product manager and directed an AI coding agent, Claude Code, to do the implementation.

  • I wrote every spec and every acceptance criterion.
  • I broke the work into 450+ scoped phases, each small enough to review on its own.
  • I reviewed every pull request before it merged.
  • I made every release decision.

The agent wrote code fast. My job was to decide what should exist, define what "done" meant, and refuse anything that did not meet it.

The quality system

A size recommendation is only useful if it is right, so every release is measured against four checks before it ships.

  • Retailer benchmark: recommendations checked against 296 real retailer listings and 11 sets of test measurements.
  • Phone benchmark: 232 store listings, each read as an iPhone page and as a computer page across the same 11 sets of measurements, so a shopper on her phone gets the same answer she would on a computer.
  • Regression replay: 8.5 million answers across 60 stores, replayed so any answer that changes is caught before release.
  • Automated tests: 12,500+ tests that must all pass before each release.

Privacy

Measured Size collects no personal data. Measurements stay on the shopper's device. There are no accounts, no tracking and no ads.

What I learned

Passing tests are not proof

"Build 94 passed every automated check, and my iPhone found the failure on Target within minutes. Our phone tests were Chrome pretending to be an iPhone, not Safari's engine. So I added a Safari-engine check to every release, and later a capture tool that turns real pages from my phone into tests, including stores that block test browsers."

The hardest call: always give an answer

When a shopper fell between two of a brand's sizes, the card used to refuse and send her to the brand's size chart. I set a new rule: never point her to a chart, give her the answer. Now the card always picks a size. When it's a close call, it shows a lower rating and a plain reason, such as "M fits your cup; the band may feel a little loose."

The rule had a cost, and I measured it. On our test benchmark, the clickable rate (cards that name a size she can choose) on Amazon fell from 100.0% to 98.0%, and overall from 97.3% to 97.1%. The drop was 12 test cards on four Amazon listings, where the card used to name a size three cups away from hers. Under the new "within two steps" rule, it names none. I accepted that as the cost of not suggesting sizes that won't fit. In the same change, right size rose from 99.0% to 99.2% on our test benchmark.

How to direct an AI coding agent

  • One phase, one concern, one pull request.
  • Every brief opens with "read the real files first," because the prompt is a summary, not the source.
  • Recompute every number fresh rather than trusting the last phase's.
  • Each phase reports back with questions, and I answer every one in writing before it merges.
  • Passing tests aren't proof. The real device is the deciding test.

What I'd do differently

I'd set the "read the real files and the latest state first" rule from day one. Early sessions worked from my prompt alone. That rule is now how every session starts.
